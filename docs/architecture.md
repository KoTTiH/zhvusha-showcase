# Архитектура ZHVUSHA

Публичный срез показывает Telegram-диспетчер, skills, runtime для делегированных
заданий, провайдеры моделей и память. Оркестратор собирает ответ пользователю;
исполнители возвращают результаты, артефакты, ошибки и предложения для памяти.

## Границы модулей

| Модуль | Ответственность |
| --- | --- |
| `src/bot/` | Telegram handlers, контекст, выбор ветки обработки и доставка |
| `src/skills/` | Отдельные функции и общий invocation lifecycle |
| `src/agent_runtime/` | Задания, профили, исполнители, разрешения и события |
| `src/llm/` | Реестр провайдеров, tiers, API- и CLI-адаптеры |
| `src/memory/` | Episodic memory, retrieval, staging и consolidation |
| `src/knowledge/` | Хранилище знаний и доступ через MCP |
| `src/daemon/` | Фоновые сигналы, Redis Streams и запуск работы |

## Сохраняемое задание

[`AgentRuntime`](../src/agent_runtime/runtime.py) создаёт job с профилем
исполнителя и контекстом. Повторное активное задание ищется по fingerprint.
Результат worker оформляется как `ContextCapsule`; события записываются отдельно,
а кандидаты памяти передаются в `AgentMemorySink`, если он подключён.

[`FileAgentJobStore`](../src/agent_runtime/storage.py) сохраняет JSON через
временный файл и замену основного. Это локальный механизм без межпроцессной
блокировки или транзакционной дедупликации. Он не обеспечивает exactly-once
исполнение внешних действий.

При восстановлении runtime помечает незавершённые `RUNNING`-задания как
`NEEDS_REVIEW`, сохраняя факт прерывания. Начать ревью удобно с
[`test_storage.py`](../tests/agent_runtime/test_storage.py) и
[`test_runtime.py`](../tests/agent_runtime/test_runtime.py).

## Разрешения и внешние действия

[`ToolGateway`](../src/agent_runtime/tools.py) проверяет capabilities и
потребность в approval. Обработчики конкретных инструментов дополнительно
ограничивают аргументы и доступные пути.
Соответствующие отказы проверяются в
[`test_tool_gateway.py`](../tests/agent_runtime/test_tool_gateway.py).

Не все действия проходят через gateway. CLI workers могут запускать subprocess
напрямую и зависят от профиля, sandbox внешнего CLI и его настроек. Наличие
capability graph не доказывает изоляцию всех интеграций. Шаблон окружения
отключает ряд внешних действий и фоновых систем; их включение требует
проверки выбранного пути исполнения.

## Skills и память

[`SkillInvocationService`](../src/skills/invocation.py) для требующих подтверждения
действий готовит план и dry-run перед approval и execute. Действия с политикой
`auto` могут выполняться сразу. Его контракт проверяется
отдельно от Telegram и внешних API в
[`test_invocation.py`](../tests/skills/test_invocation.py).

Модули памяти используют PostgreSQL и pgvector. Тесты с подменёнными
провайдерами проверяют обработку данных и переходы состояния, без измерения
полезности retrieval и фактического качества ответов LLM.

## Границы проверки

[Публичный CI](../.github/workflows/quality.yml) запускает Ruff, mypy, import smoke
и выбранные тесты runtime, invocation, уточнений Telegram и обработки памяти.
Отдельное задание запускает Gitleaks.
Import-linter настроен отдельно и в этот workflow не включён.

За пределами CI остаются реальные Telegram-сессии, LLM-вызовы, внешние действия,
миграции на пользовательской базе и эксплуатация под нагрузкой. Зелёный workflow
подтверждает перечисленные проверки конкретного коммита.
